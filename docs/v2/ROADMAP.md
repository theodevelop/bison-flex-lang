# Bison/Flex Workbench 2.0 — Roadmap

## Vision

Bison/Flex Language Support 2.0 should become the reference VS Code extension for writing, understanding, debugging and maintaining GNU Bison, Flex and RE-flex projects.

The goal is not to add a few isolated features. The goal is to evolve the extension from language support into a complete Bison/Flex workbench.

## Product Positioning

Current identity:

- Bison/Flex Language Support
- Syntax highlighting, diagnostics, completion, hover docs and helper tools

V2 identity:

- Bison/Flex Workbench
- Project-aware parser development environment
- Compiler-backed diagnostics
- Conflict exploration
- Token flow analysis
- Lexer debugging
- Safe refactoring tools

## Core Principles

1. Preserve everything that already works in V1.
2. Prefer project-aware features over isolated file features.
3. Prefer compiler-backed truth over fragile heuristics when possible.
4. Keep static analysis fast and lightweight while adding deeper analysis on save or on demand.
5. Make every advanced analysis actionable with navigation, explanations or quick fixes.
6. Keep the extension useful even when `bison`, `flex` or `reflex` are not installed.
7. Keep the architecture modular enough for agent-based development.

## V2 Pillars

### 1. Project Intelligence

The extension should understand the full parser project:

- Bison source files
- Flex / RE-flex source files
- Companion relationships between parser and scanner
- Generated `.tab.c`, `.tab.cpp`, `.tab.h`, `.hpp`, `lex.yy.c`, `.yy.cpp` files
- Generated `.output`, `.xml`, `.gv` reports
- CMake, Makefile and Automake integration
- Build directories and multi-root workspaces

Deliverable:

- Internal `ProjectModel`
- Internal `WorkspaceIndex`
- VS Code tree view: **Bison/Flex Project**

### 2. Compiler-backed Diagnostics

The current static diagnostics are useful and must remain. V2 adds optional diagnostics from real compiler output.

Modes:

- `static`: current fast static analysis only
- `compiler`: diagnostics from Bison/Flex/RE-flex only
- `hybrid`: static analysis while typing + compiler-backed validation on save or command

Deliverable:

- `bisonRunner`
- `flexRunner`
- compiler diagnostic parser
- `bisonFlex.analysis.mode` setting
- graceful fallback when tools are missing

### 3. Bison Conflict Explorer

The current conflict explanation is heuristic. V2 should use real Bison reports.

Deliverable:

- `.output` parser
- conflict model: state, lookahead, involved rules, conflict type
- conflict webview
- navigation to grammar source
- suggested fixes
- optional counterexample support when generated by Bison

### 4. Token Flow Analysis

The extension should explain how tokens move from Flex to Bison.

Deliverable:

- token declarations from Bison
- token returns from Flex actions
- string aliases and literal tokens
- semantic value type info
- missing-token diagnostics
- unused-token diagnostics across files
- Token Flow webview
- cross-file rename and quick fixes

### 5. Flex Rule Debugger 2.0

The existing rule tester should become a lexer simulation tool.

Deliverable:

- input panel
- rule matching timeline
- start condition simulation
- shadowed rule explanations
- catch-all warnings
- navigation from match to rule

### 6. Refactoring Tools

V2 should help maintain large grammars safely.

Deliverable:

- rename token across Bison and Flex
- rename non-terminal
- rename start condition
- rename abbreviation
- extract repeated Flex regex into abbreviation
- extract common Bison prefix
- move catch-all rule to bottom

### 7. Help Center and Onboarding

Deliverable:

- integrated help center webview
- diagnostic pages with examples
- project wizard for new parser/scanner setups
- C, C++, CMake and RE-flex templates

## Suggested V2.0 Scope

Minimum model:

```ts
interface BisonFlexProjectModel {
  workspaceRoot: string;
  parsers: BisonSourceFile[];
  scanners: FlexSourceFile[];
  pairs: ParserScannerPair[];
  generatedFiles: GeneratedFile[];
```

## Non-goals for V2.0

These should not block the first V2 release:

* Full LR parser implementation inside the extension
* Perfect Flex regex engine reimplementation
* Full C/C++ semantic analysis inside actions
* Full replacement for CMake Tools
* Telemetry

## Success Criteria

V2.0 is successful if:

1. A user can open a real Bison/Flex project and understand parser/scanner relationships.
2. Diagnostics can be confirmed by real Bison/Flex runs.
3. Shift/reduce conflicts become understandable from inside VS Code.
4. Token mismatches between Flex and Bison are easy to find and fix.
5. Existing V1 features keep working.
6. The README and Marketplace screenshots clearly communicate the Workbench positioning.
